Positioning

Agents API is the core. Harnesses make it useful for real workflows.

The notebook demonstrates the reusable API directly. The CLI demonstrates an agent harness built on that API. This keeps the novice surface simple while showing how serious local workflows can be assembled.

Layer 1

Agents API

Create agents, attach tools, run and continue conversations, emit traces, and persist state through adapters.

Layer 2

Concrete internals

Two demo flows: notebook in-memory, CLI file-backed.

The easiest way to understand the abstractions is through process boundaries. In notebooks, the runner, trace store, and viewer server live inside the Python kernel process. In the CLI demo, the agent writes traces and artifacts to disk while the browser reads them through the local viewer server.

1
Notebook write pathRunner writes events directly into the in-memory store through viewer.trace_sink.
2
Notebook read pathBrowser iframe calls the local viewer server, which reads that same in-memory store.
3
CLI write pathRunner writes JSONL events and tool artifacts under the selected workspace.
4
CLI read pathBrowser calls the viewer server, which reads JSONL and artifacts from disk.
5
Future productionThe same shape can point to Postgres, blob storage, and managed trace sinks.

Why split sink and store?

A sink is optimized for writes during execution. A store is optimized for reading, filtering, replaying, and powering the UI. This lets local JSONL, in-memory demo mode, Postgres, and hosted observability share the same event model.

viewer = ai.tracing.start_viewer(
    None,
    port=0,
    trace_store=ai.tracing.InMemoryTraceStore(),
)

result = ai.Runner.run_sync(
    agent,
    input,
    trace_sinks=[viewer.trace_sink],
)
Harness primitives

Toolkits turn model intent into controlled, observable actions.

A toolkit is a bundle of related tools plus metadata. The harness decides which toolkits are available, what requires approval, and how each call is traced.

Filesystem

File toolkit

Lists files, reads files, writes files, replaces text, and applies patches inside a configured root.

  • Low-risk read tools can run directly.
  • Write and patch tools require approval.
  • Large content can become artifacts.
Execution

Shell toolkit

Runs allowed commands in a configured working directory. The harness can allow specific prefixes or require approval for broader commands.

  • Command arguments are summarized.
  • stdout/stderr are traced.
  • Latency and exit code are visible.
Collaboration

Git and subagents

Git tools expose project state, while subagent tools let the main agent delegate specialized work like review.

  • Subagent runs get child trace ids.
  • Parent and child runs remain correlated.
  • The viewer can navigate between them.
Toolkits are where the harness becomes opinionated: they define what the model can do, what must be approved, what gets summarized, and what becomes observable in the timeline.
Part 4

The promotion story keeps the programming model stable.

Local development uses local stores and local sinks. Production later uses durable stores and managed sinks. The agent, tools, policies, and runner remain the same mental model.

# local
Runner.run_sync(
    agent,
    input,
    trace_sinks=[viewer.trace_sink],
)
# production later
Runner.run_sync(
    agent,
    input,
    state_store=PostgresStateStore(...),
    artifact_store=BlobArtifactStore(...),
    trace_sinks=[ManagedTraceSink(...)],
)
The takeaway: aisuite lets developers start simple, stay local, inspect every agent step, and later promote to production infrastructure without changing the core programming model.
